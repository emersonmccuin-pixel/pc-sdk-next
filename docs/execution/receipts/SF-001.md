## Delivered invariant

Before `runMigrations`, boot recovery, provider construction, or HTTP/WS listen,
production canonicalizes `PC_DATA_DIR` and must acquire both:

1. a SHA-256-addressed non-filesystem kernel witness: Windows named pipe or
   Linux abstract socket; and
2. a dedicated in-directory SQLite connection with `timeout: 0` holding
   `BEGIN IMMEDIATE` for the engine lifetime.

The kernel witness prevents POSIX unlink/recreate of the SQLite pathname from
creating a second owner. The SQLite transaction independently proves supported
filesystem write-lock behavior and makes corrupt, read-only, or otherwise
unavailable admission state fail closed. Neither PID, process start time,
heartbeat, port, file age, nor elapsed time authorizes takeover.

Normal contenders receive typed `data-directory-occupied` or
`data-directory-unavailable` before `pc.sqlite` is opened. Distinct canonical
directories remain independent. Release is idempotent for controlled tests and
handoff, while production deliberately retains the kernel witness until actual
process exit. The restart child has a bounded contention retry, but it can only
continue after a positive acquisition; the bound can only fail.

Shutdown synchronously gates new HTTP fetches, upgrades, and
`SessionRegistry.get()` before taking session snapshots. Registry and dispatch
attempt all tracked disposals with `allSettled`; synchronous and asynchronous
close failures remain explicit. The active orchestrator runtime no longer
converts a failed close to success. The product DB closes only after those
tracked operations settle. The witness still remains authoritative until the
process exits, so incomplete bookkeeping cannot admit a successor engine.

passed 11/11:

1. normalized and junction aliases collide; distinct directories coexist;
   explicit release is fenced and idempotent;
2. empty/invalid paths, injected `EACCES`, and corrupt SQLite fail unavailable
   without `pc.sqlite` creation or destructive repair;
3. replacing the admission pathname cannot bypass the kernel witness; a
   restart waiter remains blocked until a positive acquisition;
4. a real child contender exits occupied before its admitted callback;
5. the real production entrypoint exits 73 before migration/provider startup;
6. two child processes with distinct directories coexist and graceful handoff
   admits a successor;
7. hard-killing the owner permits reclaim and two simultaneous reclaimers
   produce exactly one winner;
8. source guards place admission before migration/composition/listen and retain
   the production witness through actual exit; launcher exit handling is inside
   the process-exit polling branch;
9. specialist disposal waits, attempts every session even after a synchronous
   throw, and propagates uncertainty;
10. active orchestrator disposal failure remains a shutdown failure; and
11. server shutdown closes HTTP and registry admission before a blocked
    disposal snapshot settles.

On the Windows verification host, deleting the live SQLite path returned
`EBUSY`; the same test performs the actual replacement on POSIX filesystems
that permit it, where the independent abstract-socket witness remains the
owner door. No fixed port, PID liveness inference, provider call, or success
sleep is used. Test-only time bounds fail the harness; they never mint an
ownership receipt.

## Deliberate boundary

SF-001 proves one PC-SDK engine per canonical app data directory. It does not
claim positive exit of every provider, setup, verification, or repository child
process. Those processes receive no authority from the admission receipt; the
cross-process repository lease (SF-002), child-environment scrub (`SEC-003`),
and later process hardening own those separate risks. It also does not implement
loopback listener binding (`OPS-006`) or daily-driver promotion.

`OPS-005` therefore remains `accepted`, not globally verified, until the
repository-lease half lands.
