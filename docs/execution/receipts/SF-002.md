## Delivered invariant

For every configured Git-backed runtime cwd, PC-SDK Next now resolves the
native real path of Git's absolute common directory and acquires one
engine-lifetime, re-entrant repository lease before write-capable activity.
The lease combines:

1. a protocol-stable, SHA-256-addressed Windows named pipe or Linux abstract
   socket; and
2. a zero-wait SQLite `BEGIN IMMEDIATE` held in the Git common directory.

Main checkouts, subdirectories, filesystem aliases, and linked worktrees of one
repository converge on one identity. Distinct local repositories remain
independent. Same-engine builders may continue in separate worktrees, while
the existing in-process FIFO still serializes landing and stale-base
revalidation.

Project creation now carries the selected mode into the authority door and
revalidates the current filesystem state there. `init-empty` accepts only an
empty non-Git directory, `init-in-place` accepts only a nonempty non-Git
directory, and neither mode silently attaches a repository that appeared after
the UI probe. `attach-to-git` accepts an existing canonical worktree root and
refuses a selected repository subdirectory rather than rewriting the project
path to the discovered root. Mode/state drift and root mismatch return HTTP
409 before a project row or Git-side effect is created.

Initialization claims the anticipated `<project>/.git` identity before Git
starts, writes a crash-visible bootstrap-pending marker, and commits a clean
`Initial scaffold` for an empty directory or `Initial import` for adopted
files. The marker is removed only after Git resolves the anticipated common
directory and the initialized repository is clean; an incomplete marker is
typed unavailable and is never inferred safe from age or process absence.

The authority guard covers fresh provision, setup/readiness, continuation and
automatic continuation, runtime create/resume, deliverable sealing,
verification, review checkout/runtime/reclaim, accept-time revalidation,
landing, teardown, branch deletion, orphan pruning, and recovery. Because the
pinned native permission mode is not a read-only sandbox, admission also covers
orchestrator, payload, and review runtimes whose cwd is Git-backed.

Every fresh repository run durably stamps an exact `git-common-dir-v1`
receipt. SQLite guards require a complete shape, freeze it after insertion, and
require continuations to inherit the exact parent receipt. Retained legacy
receipts remain readable evidence but cannot be promoted into mutation
authority. Project-path or worktree-path retargeting is rejected before a
later door can read or persist foreign Git evidence.

Project rows are born with or atomically bind that same durable identity, and
worktree receipts carry it through the run. Boot recovery and landing pass the
stored receipt as an expected identity during acquisition, then revalidate it
under the live guard before classifying, merging, pruning, or cleaning up.

Ambient `GIT_DIR`, `GIT_WORK_TREE`, and `GIT_COMMON_DIR` are removed at all
three app-owned child seams: direct Git commands, setup/readiness/verification
shell commands, and provider runtime environments. Repository selection is
therefore cwd-derived at the same path whose authority was proved.

Migrated projects that have a nonempty folder but no repository identity fail
native continuation honestly. Historical availability/resume and active
restart remint return typed `repository-identity-unavailable` before runtime
preflight, durable continuation-state changes, or active-session replacement.

The app-owned sibling worktree root must be a real directory. A symlink or
Windows junction cannot redirect provision, review checkout, teardown, or
recursive orphan cleanup outside that root.

## Deliberate boundary

SF-002 is a cooperative same-host protocol. The preserved working PC-SDK does
not implement it, nor do manual Git/IDE processes or unrelated tools. The
manual prohibition on configuring the working app and PC-SDK Next for
write-capable work against the same external repository at the same time
remains mandatory.

The lease belongs to the server process. A provider, setup, verification, or
Git child that survives a hard-killed server is not contained by this receipt.
No supervisor/helper process was introduced. SF-002 removes only the three
ambient Git repository selectors at Git, shell, and provider seams; `SEC-003`
still owns the general child-environment allowlist/secret scrub, and later
process hardening owns escaped-child containment. Remote-host and network-
filesystem exclusion also remain outside this slice.

Consequently `OPS-005` remains `accepted`, not globally `verified`, and SF-002
does not claim the full N4 process-failure gate. `OPS-006` loopback binding and
N7 daily-driver work remain separate.
