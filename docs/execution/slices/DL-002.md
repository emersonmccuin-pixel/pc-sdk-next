# DL-002: Browser-approved worktree abandonment

Status: complete — sealed, guarded-landed, post-merge verified, pushed, and
feature worktree removed

## Objective

Implement the explicit approved-abandonment half of the worktree lifecycle.
Removing unlanded repository work requires a browser-attributed user approval,
an immutable authority receipt, positive teardown settlement, and crash-safe
re-drive. Landing and abandonment are mutually exclusive. The feature branch
is preserved at its approved tip; the worktree directory plus any uncommitted
or untracked contents are removed only after authority is durable.

## Requirements and boundaries

- Primary requirements: `WT-005` and `WT-006`; this slice also strengthens
  `SEC-002`, `UI-001`, and the N4 delivery gate.
- Boundary documents: `docs/architecture/boundaries.md`,
  `docs/agent-runtime-architecture.md`, `docs/worktree-lifecycle.md`, and
  `docs/pickup-protocol.md`.
- Contracts own approval and settlement receipts. Landing owns repository
  inspection, per-repository serialization, teardown, and recovery. The
  browser surface collects typed confirmation but never authors authority
  fields. Attribution is bounded to the existing trusted-local-process model;
  fetch metadata is CSRF hardening, not cryptographic proof of human presence.
- DB state is authoritative. `abandoning` means approval is durable and
  teardown is incomplete; only positive settlement may write `abandoned`.
- Existing `abandoned` rows with no authority/settlement receipts are legacy,
  visible, and non-destructive. Migration never fabricates approval.

## Canonical preview and approval contract

The server returns a strict preview:

```ts
interface WorktreeAbandonmentPreview {
  protocol: 'worktree-abandonment-preview-v1';
  projectId: ULID;
  contractId: ULID;
  contractVersion: number;
  producerRunId: ULID;
  worktreeId: ULID;
  worktreeStatus: 'active' | 'stranded';
  worktreePath: string;
  branch: string;
  branchTip: string;
  baseBranch: string;
  validatedBaseSha: string;
  targetTip: string;
  integrationState: 'unmerged' | 'no-exclusive-commits';
  repositoryIdentity: RepositoryIdentityReceipt;
  worktreeState:
    | {
        directory: 'present';
        registration: 'registered';
        status: 'clean' | 'dirty';
        staged: number;
        unstaged: number;
        untracked: number;
        worktreeStateDigest: `sha256:${string}`;
        changedPaths: string[]; // bounded, display-only summary
        ignoredContents: 'uninspected';
      }
    | {
        directory: 'missing';
        registration: 'registered' | 'absent';
        status: 'unavailable';
        worktreeStateDigest: `sha256:${string}`;
        changedPaths: [];
        ignoredContents: 'uninspected';
      };
  previewDigest: `sha256:${string}`;
}
```

Approval accepts only:

```ts
{
  requestId: string; // UUID, generated once per modal attempt
  expectedContractVersion: number;
  previewDigest: `sha256:${string}`;
  confirmation: string; // exact branch name
  reason?: string; // trimmed, bounded; null when absent
}
```

Unknown fields fail. In particular callers cannot submit `actor`,
`approvedBy`, `approvalSurface`, producer, path, branch, tip, repository
identity, worktree state, or a receipt. Both routes require
`Sec-Fetch-Site: same-origin`; approval also requires JSON content type.

Once revalidated, the server persists:

```ts
interface WorktreeAbandonmentReceipt {
  protocol: 'worktree-abandonment-v1';
  requestId: string;
  approvedBy: 'user';
  approvalSurface: 'browser';
  approvalReason: 'explicit-browser-confirmation';
  approvedAt: number;
  reason: string | null;
  approvedContractVersion: number;
  projectId: ULID;
  contractId: ULID;
  producerRunId: ULID;
  worktreeId: ULID;
  worktreeStatus: 'active' | 'stranded';
  repositoryIdentity: RepositoryIdentityReceipt;
  worktreePath: string;
  branch: string;
  branchTip: string;
  baseBranch: string;
  validatedBaseSha: string;
  targetTip: string;
  integrationState: 'unmerged' | 'no-exclusive-commits';
  worktreeState: WorktreeAbandonmentPreview['worktreeState'];
  previewDigest: `sha256:${string}`;
}
```

Approval requires the present/registered preview variant. A missing worktree
may be reported diagnostically but cannot create fresh authority. After
authority exists, recovery may settle a now-missing directory only by proving
registration absence and exact branch preservation.

Positive settlement records:

```ts
interface WorktreeAbandonmentTeardownReceipt {
  protocol: 'worktree-abandonment-teardown-v1';
  authorityRequestId: string;
  startedAt: number;
  finishedAt: number;
  repositoryIdentity: RepositoryIdentityReceipt;
  worktreePath: string;
  branch: string;
  approvedBranchTip: string;
  observedBranchTip: string;
  directoryAbsent: true;
  registrationAbsent: true;
  branchPreserved: true;
}
```

Cross-field rules are exact:

- `abandoning`: authority present, teardown receipt null;
- new `abandoned`: matching authority and teardown receipts present;
- legacy `abandoned`: both receipts null, authority unavailable;
- every other landing status: both receipts null;
- any partial/mismatched final receipt combination is invalid.

`abandonmentError` is nullable and may be populated only while `abandoning`;
it is cleared by positive settlement. Receipt fields are immutable. The state
digest is NUL-safe and content-binding: it hashes canonical porcelain evidence,
tracked binary diff bytes, and deterministic untracked path/content hashes.
Ignored/generated contents are deliberately not inspected and the browser
states that they will still be removed.

## Mutation and recovery semantics

Preview is read-only. Approval enters the same repository queue used by
landing and repeats every mutable Git/DB check under the held lease. The
dedicated DB reservation CAS binds contract ID/version/producer/landing state
to the exact server-derived receipt and publishes its contract outbox frame in
the same transaction. This reservation wins before recursive removal; once it
commits, a failure returns durable `202 pending`, never an error implying that
nothing changed.

Teardown removes only the approved app-owned worktree. It never runs cleanup
commands and never deletes or moves the feature branch. Settlement re-reads
directory absence, registration absence, and branch tip. Only the dedicated
matching-request CAS may change `abandoning` to `abandoned` and publish the
settled contract frame.

Worktree-row settlement is also exact: row ID, contract ID, recorded path, and
active/stranded state must match before it becomes destroyed. Basename-wide
row mutation is not abandonment authority.

Landing, continuation, review, and new abandonment refuse an `abandoning`
contract. Landing and abandonment cannot both reserve the same contract.
The DB continuation insert itself rechecks the current contract landing state,
and abandonment reservation rejects every nonterminal run bound to the
contract; service checks alone are not race authority. Landing reservation is
also an exact version/state CAS rather than the prior generic setter.
Late deliverable, verification, review, producer-binding, and ordinary landing
mutations refuse once abandonment authority exists.
Replaying the same request is idempotent; a different request cannot take over
existing authority. Boot re-drives durable `abandoning` receipts through the
same queue before stranded scan/orphan cleanup. Legacy `abandoned` rows never
enter recovery without a new explicit browser approval, but are eligible for a
fresh approval when all current Git/worktree evidence is still provable.

Integration evidence is tri-state and fails closed. Inspection resolves the
exact branch/base refs, proves `validatedBaseSha` is an ancestor of the branch
tip, and counts `validatedBaseSha..branchTip`. Zero exclusive commits is an
eligible explicit `no-exclusive-commits` state. Otherwise Git must positively
return “not ancestor” for branch tip versus current target tip to record
`unmerged`; already-ancestor means already merged and refuses, while missing
refs or any inconclusive Git result refuses. The generic landing convergence
probe is not reused because its `landed: false` combines negative and unknown.

## Browser semantics

The Activity panel exposes a direct contract-bound action on eligible
merge-ready/landing-issue and stranded-worktree cards; canceled producers may
not have a retained run row, so abandonment never depends on transcript
navigation. The repository run transcript is a secondary entry point when the
run remains available. Both open the same contract-ID modal and load a fresh
preview. The explicit-close modal shows path, exact branch/tip, dirty
counts/digest, and states that the branch is not merged, committed history
stays on the branch, and the worktree plus all uncommitted/untracked contents
will be removed. The action remains disabled until the exact branch name is
typed and the preview is eligible.

For `no-exclusive-commits`, the browser says there is no branch-only commit to
merge rather than claiming an unmerged change. For `unmerged`, the persisted
base/target/ancestry evidence supports the explicit “not merged” wording.

`abandoning` remains an activity issue. Receipt-backed final `abandoned` is
resolved. Legacy `abandoned` without authority/settlement remains visible as
authority unavailable and non-destructive. Transcript wording distinguishes
approval pending, settled branch preservation/not-merged, and legacy
unavailability; it never renders abandonment as a merge receipt.

## Acceptance criteria

1. No registered generic landing, chat, MCP, prompt, specialist, or
   orchestrator-tool product door can author abandonment authority.
2. Preview proves exact project/contract/producer/repository/path/registration/
   branch/tip/content evidence and returns a deterministic NUL-safe digest.
3. Non-browser, cross-site, non-JSON, unknown-field, forged-actor, malformed,
   stale-version, stale-preview, and confirmation-mismatch requests fail before
   durable approval or filesystem mutation.
4. Live or still-disposing producer/reviewer/continuation, pending landing,
   landed work, existing different approval, unowned/unregistered/drifted
   paths, missing identity or branch, changed tip/status, and positively merged
   work refuse.
5. Approval CAS and outbox commit atomically before teardown; no fresh approval
   is minted for a missing directory.
6. Teardown removes the worktree and uncommitted/untracked content without
   cleanup commands or branch deletion; settlement proves exact branch tip,
   directory absence, and registration absence.
7. Only matching settlement writes final `abandoned`. Same request is
   idempotent; a different request cannot steal or overwrite authority.
8. Crash/restart before removal, after removal, or before settlement re-drives
   safely from `abandoning`; uncertainty stays pending and visible.
9. Landing/abandonment and continuation/abandonment races have exactly one
   winner. A child paused after preflight/lease cannot insert after either
   reservation wins, and no mutation follows stale authorization.
10. Legacy `abandoned` rows retain null receipts, authorize no cleanup, remain
    visibly unresolved, and stay protected from orphan deletion; only
    receipt-backed final abandonment resolves.
11. Strict DTO/resource projection, migration/outbox replay, HTTP statuses,
    modal confirmation/loss warning, activity classification, and transcript
    receipt wording pass focused guards.
12. Actual-path audit, `git diff --check`, hostile review, full
    `pnpm ci:check`, sealed commit, guarded landing, ancestry/tree proof,
    post-merge gate, exact push/re-fetch, and worktree teardown pass.

## Risk and recovery

- Primary risks: fake actor attribution, deleting before approval durability,
  stale preview authority, racing a merge/continuation, deleting outside the
  owned sibling root, losing uncommitted work without explicit warning,
  deleting/drifting the retained branch, false settlement, replaying old DTOs,
  or treating legacy `abandoned` as approval.
- Recovery: before authority, every uncertainty refuses with no mutation.
  After authority, `abandoning` is the durable truth and boot re-drives only
  the exact approved path/tip under the repository queue. Missing settlement
  never means success.

## Deliberate security boundary

`Sec-Fetch-Site: same-origin`, strict JSON, typed confirmation, and the absence
of any app tool/MCP route provide a browser-surface approval boundary against
cross-site requests and normal product automation. They do not prove OS-level
human presence against another trusted local process that can forge HTTP
headers and call the loopback server directly. Current write-capable runtimes
also lack loopback/network containment. DL-002 therefore records
`approvalSurface: browser` under the cooperative trusted-local-process model;
it does not claim unforgeable user identity or complete `SEC-002`. Loopback
binding and runtime/process containment remain explicitly deferred with
`OPS-006`/the broader security gate.
