## Objective

Complete the deferred N1 joint inspection of AInativePM's code, domain,
persistence, UI, REST, and MCP surfaces together with every existing PC-SDK
touchpoint. Produce an evidence-backed ownership seam, typed integration-port

surfaces. It may end in a product-direction decision, but evidence gathering and
proposal synthesis do not require that decision up front.

## Scope

In scope:

- AInativePM domain and persistence map: generic items/types/behaviors, domain
  hierarchy, membership, assignment, stages/status, decisions, context,
  attachments, links, rules, views, templates, calendars, and durable events;
- UI/REST map of how a person creates, organizes, assigns, discusses, reviews,
  completes, archives, and revisits work across software and non-software
  domains;
- MCP map: exact commands/queries, shared-core parity, auth/account/project
  resolution, hidden admin surface, idempotency/retry behavior, health,
  unavailable/degraded states, and current consumers;
- PC-SDK map: `pmRef`, contracts, agent runs, pending asks, deliverables,
  verification/landing evidence, prompts, MCP registry/bridge, project context,
  and every provisional anchoring assumption;
- one ownership table stating which system owns status, assignment, decisions,
  progress, evidence, identity, deletion, and disagreement resolution;
- interaction sequences for reference/dispatch, progress/evidence, completion,
  retry/duplicate delivery, PM outage, deletion, and conflicting state;
- a provider-neutral typed PM port proposal with explicit query/command/event

  boundaries;
- explicit classification of future updates as automatic, suggested, or
  user-approved, plus deep-link/reference direction without copied truth;

  writes, or a general work-item system;
- reading secret values from `.env`, credential stores, or databases when code

## Acceptance criteria

1. The source receipts fix both repositories and show clean/pushed state before
   inspection; the final path audit proves AInativePM stayed unchanged.
2. The deliverable maps AInativePM's generic domain/persistence model and its
   real UI workflows without reducing the product to software work items.
3. REST and MCP are traced to shared core operations, including auth/scope,
   hidden admin tools, health, retries, idempotency, and typed failure behavior.
   Unknown or absent behavior is recorded as unknown, not inferred.
4. Every current PC-SDK PM seam is mapped from public contract through durable
   state, dispatch/prompt use, safe projection, and MCP composition. `pmRef`
   remains a reference, never silently promoted into copied PM truth.
5. One ownership table assigns long-lived intent, hierarchy, status, assignment,
   decisions, discussion/context, execution state, verification, Git delivery,
   artifacts/evidence, deletion, and audit provenance to exactly one authority
   or an explicit reference boundary.
6. Interaction sequences cover happy path, duplicate/retry, timeout, outage,
   stale/deleted references, conflicting state, cancellation, and recovery.
   Timeouts and missing evidence never imply PM success.
7. The typed port proposal separates queries from side-effecting commands,
   requires idempotency keys and positive receipts for every future write, and
   defines visible unavailable/degraded/inconclusive states.
8. Proposed automatic, suggested, and user-approved actions are explicit. No
   automated PM write is recommended without a proven ownership and replay rule.
9. The provisional folder-binding/token/explicit-project anchor assumptions are
   individually verified, rejected, or left unknown with evidence; the old
   implementation proposal is superseded rather than silently retained.
10. Independent domain, UI, MCP, and PC-SDK-touchpoint reviews converge into one
    proposal. Read-only browser/MCP checks expose no secrets in the receipt and
    leave the remote unchanged.
