# SEC-003: Least-privilege child environments

Status: active

## Objective

Replace broad server-environment inheritance at every production provider
runtime, repository, setup, readiness, verification, and cleanup child seam
with one provider-neutral positive allowlist. Runtime adapters may add only the
credential-home selector that PC-SDK selected for that runtime. Unknown and
unrelated variables, including `PC_AINATIVE_PM_TOKEN`, raw provider/API
credentials, app data paths, ambient Git selectors, and shell-injection
controls, must not reach repository-controlled code or persist through command
output receipts.

through its existing typed preparation/readiness/verification behavior until a
later explicit local-input policy exists. That fail-closed result is the
accepted least-privilege behavior, not permission to retry with the server
environment.

## Scope

In scope:

- one pure positive-allowlist builder for app-owned child environments;
- platform-aware preservation of only the OS execution, home, temporary,
  locale, and terminal variables needed to launch normal commands;
- exact-name behavior on case-sensitive platforms and case-insensitive
  collision handling on Windows, with ambiguous duplicates dropped;
- rejection of undefined, NUL-bearing, and exported-shell-function values;
- provider-runtime discovery, create, resume, and direct-session defense in
  depth, with exactly the selected Claude `CLAUDE_CONFIG_DIR` added after the
  inherited environment is reduced;
- setup, readiness, verification, cleanup, and their descendant processes via
  the one shell executor, including caller-supplied base environments;
- all app-owned Git subprocesses because checkout filters, hooks, and helpers
  can execute repository-controlled code before a provider runtime starts;
- the fixed Windows process-tree termination helper;
- preservation and source/test classification of the MCP stdio boundary: the
  MCP SDK's safe default environment plus explicitly attached per-server env is
  intentional consumer policy, not ambient server inheritance;
- static guard coverage that makes a new production child-process seam or a
  return to `process.env` spreading fail review/tests.

- filesystem, network, tool, or native-provider sandboxing; scanning command

## Canonical decisions

The inherited environment starts empty. On Windows it may retain only the
approved system execution, user-home/config, temporary, locale, and terminal
variables; on POSIX it may retain only the corresponding exact uppercase
names. `PATH`, shell/system roots, home/config roots, and temporary directories
remain available so the SDK and ordinary project commands can launch. Proxy,
certificate, package-manager, compiler-injection, dynamic-loader, SSH-agent,
Git-selector, app-owned, provider-owned, and unknown variables do not inherit.

Windows matching is case-insensitive because the OS environment is
case-insensitive. A supplied object containing more than one spelling of an
allowed name is ambiguous and that name is omitted rather than selecting a
value by property order. POSIX matching remains exact so a lowercase lookalike
cannot be promoted into an executable uppercase variable. The input object is
never mutated.

The Claude adapter adds one exact `CLAUDE_CONFIG_DIR` only after allowlisting.
Ambient Claude/Codex homes, Anthropic/OpenAI endpoints or keys, and raw auth
tokens are never honored. The final `ClaudeRuntimeSession` query seam sanitizes
again so constructing a session with a custom dirty environment cannot bypass
the account registry. There is no broad-environment fallback on spawn failure.

The shared Git environment helper is removed after every direct Git consumer
moves to the general policy. This preserves SF-002's cwd-derived repository
authority while also preventing filters/hooks/helpers from observing unrelated
server capabilities.

MCP stdio remains separate: its SDK already starts from a small OS allowlist
and merges only stored `config.env` supplied for that registered consumer.
Those explicit values are not ambient inheritance and must not be silently
removed by this slice.

## Acceptance criteria

1. Pure cross-platform tests prove that only the documented allowlist survives,
   inputs remain unchanged, unknown/PM/app/provider/Git/injection variables are
   absent, and undefined, NUL, shell-function, mixed-case, and duplicate-key
   cases fail closed.
2. Claude model discovery, fresh create, native resume, and a directly
   constructed runtime session all pass a safe environment with exactly the
   selected credential home. Raw API credentials cannot shadow subscription
   login, and there is no API-billing fallback.
3. A pinned-SDK fake spawn captures the final native process environment
   without a provider call. Only the allowlisted input, selected home, and
   documented SDK-authored markers survive.
4. Real shell/grandchild guards prove setup, readiness, verification, and
   cleanup cannot read ambient PM, arbitrary, provider, Git, or injection
   canaries while ordinary PATH/home/temp-based commands and existing typed
   receipts still work.
5. A controlled repository filter/hook/helper invoked by app-owned Git cannot
   observe an ambient canary, and the existing SF-002 selector/cwd tests remain
   green.
6. The MCP stdio guard proves an ambient canary is absent while an explicitly
   configured attachment value remains present. Engine replacement remains an
   explicit trusted exception; no other production runtime/setup/Git child
   bypass is unclassified.
7. Focused tests, static actual-path/source audits, `git diff --check`, hostile
   review, full `pnpm ci:check`, sealed commit, guarded landing, ancestry/tree
   proof, post-merge gate, push, and worktree teardown pass.

- Primary risks: retaining a compatibility wildcard, case-collision selection,
  sanitizing only the account registry rather than the final runtime seam,
  leaving Git filters/hooks broad, breaking PATH/home essentials, scrubbing
  explicit MCP attachment env, or falling back to `process.env` after failure.
- Recovery: unknown input is omitted, ambiguous platform state fails closed,
  and existing typed preparation/verification/runtime failures preserve work.
  A failed gate leaves this isolated branch/worktree intact while `main`
  remains read-only.
