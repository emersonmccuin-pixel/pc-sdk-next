# SF-002: Cooperative cross-process repository lease

Status: active — contract defined before implementation

## Objective

Give one cooperating PC-SDK engine exclusive same-host authority over one
canonical Git repository while that engine remains alive. The first
repository-writing action acquires an engine-lifetime, re-entrant lease keyed
to the repository's canonical Git common directory. Same-engine runs may still
build concurrently in isolated worktrees, while a second updated engine using
a different PC-SDK data directory fails closed before it can provision, run,
review, verify, land, recover, prune, or tear down work in that repository.

## Requirements and boundaries

- Requirement IDs: a bounded cooperative portion of `OPS-005` and `WT-004`.
- Boundary documents: `docs/architecture/boundaries.md`,
  `docs/worktree-lifecycle.md`, `docs/agent-runtime-architecture.md`, and
  `docs/pickup-protocol.md`.
- Workspaces owns repository identity, lease admission, and the authority
  guard. Landing retains its existing process-local FIFO queue and owns the
  guarded merge/receipt/teardown state machine.
- Repository identity is the native real path returned from
  `git rev-parse --path-format=absolute --git-common-dir`, not the mutable
  project-row spelling, remote URL, working-tree root, branch, or data
  directory.
- Ownership uses a protocol-stable SHA-256-addressed Windows named pipe or
  Linux abstract socket plus fail-closed repository-local admission state. It
  never grants takeover from a PID, heartbeat, timestamp, missing file, or
  elapsed time.

This slice is deliberately cooperative. The preserved working PC-SDK does not
implement the protocol, and an already-running repository child may outlive a
hard-killed server. SF-002 therefore does not mark all of `OPS-005` verified,
does not relax the working-PC-SDK/Next concurrent-write prohibition, and does
not claim the full N4 process-failure gate. Child authority/containment remains
with `SEC-003` and later process hardening under the existing one-server/no-
supervisor product boundary.

## Scope

In scope:

- discover and durably stamp one canonical Git common-directory identity at
  fresh worktree provision, then revalidate it before every later authority
  door;
- acquire one engine-lifetime, process-wide, re-entrant lease before the first
  mutation for that identity and retain it until actual engine exit;
- preserve same-engine parallel isolated builders and the existing local
  per-repository landing queue;
- gate fresh provision, setup/readiness, continuation/auto-continuation,
  runtime create/resume, deliverable sealing, verification commands,
  independent-review checkout/runtime/reclaim, accept-time revalidation,
  merge/receipt/teardown/branch deletion, orphan sweep, and their boot-recovery
  equivalents;
- return typed acquired/occupied/unavailable/released test receipts. Occupied
  or uncertain authority affects only that repository, performs no mutation,
  and never blocks unrelated chat or distinct repositories;
- deterministic real-process guards for common-directory aliases, linked
  worktrees, distinct repositories, hard process death, simultaneous
  acquisition, losing-process non-mutation, occupied recovery, and fixture
  cleanup.

Out of scope:

- participation by the immutable working PC-SDK, manual Git/IDE processes, or
  unrelated tools that do not implement this cooperative protocol;
- authority inherited by provider, setup, verification, or Git children after
  the owning server is hard-killed; no helper/supervisor process is introduced;
- remote-host or network-filesystem exclusion and repositories related only by
  a shared remote URL;
- child environment allowlisting/scrubbing (`SEC-003`), listener binding
  (`OPS-006`), N7 launcher/service/accessibility/migration work, provider-
  specific changes, or a workflow engine;
- a replacement for Git's own ref/index/object locking or the existing local
  landing FIFO.

## Canonical decisions

The identity protocol requires Git's absolute common-directory result and
native filesystem canonicalization. Main checkouts, subdirectories, junctions
or symlinks, and linked worktrees of one repository must converge; distinct
clones remain distinct. The provision receipt freezes that identity so a later
project-path retarget cannot redirect an existing run into another repository.

The process-wide manager caches one live guard per identity. Re-entrant access
inside that engine shares the guard, permitting the already-designed parallel
worktree model. A second cooperating process receives typed contention with no
wait-based takeover. The stable witness namespace is not versioned with
"Next", so another PC-SDK build can adopt the same protocol later without
creating a bypass.

The lease is acquired before any Git or command evidence used to authorize a
mutation, and the identity is re-read under the guard. Landing keeps the guard
through re-read, merge, durable app receipt, teardown, and branch deletion.
Release uncertainty fails closed. Production does not voluntarily release a
repository guard during graceful restart; explicit release exists only for
bounded tests and controlled teardown evidence.

## Acceptance criteria

1. Two independent updated server/fixture processes using distinct app data
   directories cannot both acquire one Git common-directory identity. The
   loser receives `repository-occupied` before any branch, worktree, command,
   runtime callback, merge, teardown, prune, or deletion side effect.
2. Root, subdirectory, normalized, filesystem-alias, and linked-worktree paths
   for one repository collide. Distinct repositories can be owned
   concurrently. Windows case-sensitive directories are not globally folded.
3. Same-process repeated acquisition returns the same live authority and
   same-engine parallel isolated builders remain possible. The existing local
   landing queue still serializes merge mutation and stale-base revalidation.
4. Every app-owned repository-writing and recovery door named in Scope proves
   a current guard before action. An occupied repository is skipped/preserved
   without blocking boot recovery for unrelated repositories.
5. Graceful explicit test release permits a successor. Hard-killing the engine
   releases its live OS/file witnesses; simultaneous successors admit exactly
   one. No PID, heartbeat, stale metadata, missing file, or elapsed time grants
   ownership.
6. The immutable provision receipt rejects repository-identity drift before
   continuation, resume, verification, review, landing, or teardown.
   Corrupt, symlinked, permission-denied, unsupported, or unresolvable lease
   state is typed unavailable and never repaired into authority.
7. Tests explicitly retain the escaped-child and non-participating stable-app
   limitations. `OPS-005` remains accepted, and the existing manual prohibition
   remains in force after this slice.
8. Focused real-process tests, actual-path/source audits, hostile review, full
   `pnpm ci:check`, sealed commit, guarded landing, ancestry/tree proof,
   post-merge gate, push, and worktree teardown pass.

## Risk and recovery

- Primary risks: keying a working-tree spelling rather than Git common-dir,
  releasing per run, gating only `landBranch`, allowing a project-path retarget,
  deleting corrupt/stale state, blocking unrelated repositories, nested lock
  deadlock, or claiming authority over non-participants/escaped children.
- Recovery: every missing, mismatched, occupied, or uncertain guard fails
  closed and preserves existing work. OS release after process death permits a
  later positive acquisition; ambiguity never authorizes cleanup or merge.
