# SF-001: Data-directory single-instance admission

Status: active

## Objective

Give one PC-SDK engine exclusive ownership of one canonical app data directory
for its entire lifetime. Admission must succeed before the product database,
migrations, boot recovery, runtime composition, or HTTP/WS listener can start.
A second engine targeting the same directory fails closed with an explicit
typed result, while engines using distinct directories remain independent.

## Requirements and boundaries

- Requirement ID: the data-directory admission half of `OPS-005`.
- Boundary documents: `docs/architecture/boundaries.md`,
  `docs/worktree-lifecycle.md`, and `docs/pickup-protocol.md`.
- Launcher/operations owns process and data-path admission. Product database
  state and component recovery remain owned by persistence/recovery.
- The lock is OS-enforced SQLite file ownership in a dedicated admission file,
  not a PID, heartbeat, age, port, or timeout heuristic. Process death releases
  the live lock through the operating system; stale metadata never authorizes
  takeover.

This slice does not implement the cross-process repository lease that completes
`OPS-005`. It also does not change child-process environment policy
(`SEC-003`), listener binding (`OPS-006`), accessibility, packaging, shortcut
installation, or daily-driver promotion.

## Scope

In scope:

- canonicalize and positively create/resolve the configured data directory;
- acquire a zero-wait lifetime write transaction in a dedicated SQLite
  admission database before any product-state mutation or listener activity;
- return closed acquired/occupied/unavailable/released receipts without
  guessing from PIDs, process start times, stale files, or elapsed time;
- retain the admission handle across startup and release it exactly once after
  normal shutdown or before a requested replacement process is spawned;
- release on startup failure and fail restart closed when release is not
  positively acknowledged;
- emit stable occupied/unavailable process exit codes and make the hidden
  launcher surface those states immediately;
- cross-process guards for same-directory exclusion, distinct-directory
  coexistence, graceful handoff, forced-process-death recovery, path aliases,
  corrupt admission state, and startup ordering.

- repository-scoped leases or changes to the process-local landing lock;
- any product schema migration, durable business event, or browser UI state;
- remote filesystem guarantees beyond SQLite's supported filesystem locking;
- listener host changes, port ownership redesign, or a supervisor process;
- PID/heartbeat owner inspection or automatic stale-record deletion.

## Canonical decisions

The admission database is separate from the product database. A dedicated
`better-sqlite3` connection opens it with `timeout: 0` and holds
`BEGIN IMMEDIATE` for the engine lifetime. `SQLITE_BUSY`/`SQLITE_LOCKED` is
positive contention evidence. Open, permission, path, or integrity failures are
typed unavailable and cannot fall through into application startup.

The live SQLite lock is authoritative. No persisted PID or timestamp can prove
ownership, so none is used to reclaim the directory. After a hard crash, a new
process may proceed only when SQLite positively grants the write transaction.
The persistent admission file is retained; corruption is evidence to stop, not
permission to delete and retry.

## Acceptance criteria

1. Source and process guards prove admission occurs before `runMigrations`,
   boot recovery, runtime/provider initialization, and HTTP/WS listen. A failed
   contender performs none of those actions.
2. Two independent processes targeting the same canonical directory cannot
   both receive an acquired receipt. The loser immediately receives
   `data-directory-occupied`; no wait expiry is treated as success.
3. Different canonical directories can be held concurrently. Relative and
   normalized aliases of one directory collide on the same admission file.
4. Graceful release permits a successor, and forced holder termination permits
   a successor only after the operating system releases SQLite ownership. PID
   reuse, missing metadata, and elapsed time play no role.
5. Missing directories are created and canonicalized. Corrupt admission files,
   invalid paths, permission failures, and non-contention SQLite failures return
   `data-directory-unavailable` and do not start the engine.
6. Restart closes live services, positively releases admission, and only then
   spawns the replacement. Shutdown/startup-failure paths release once; a
   release failure blocks respawn.
7. The hidden launcher distinguishes occupied from unavailable startup exits
   without waiting the full health timeout and points to the exact data path and
   error log.
8. Focused cross-process tests, source/allowed-path audits, independent hostile
   review, full `pnpm ci:check`, sealed commit, guarded landing, ancestry/tree
   proof, post-merge gate, push, and teardown pass.

## Risk and recovery

- Primary risks: acquiring after a product mutation, allowing timeout/PID
  heuristics to become takeover authority, releasing before mutation stops,
  spawning a replacement before release, or leaving child fixtures alive.
- Recovery: every ambiguous admission or release fails closed; process death
  lets the OS release live handles; failed gates preserve this worktree while
  `main` remains read-only.
