# SF-001: Data-directory single-instance admission

Status: complete — guarded-landed, pushed, and feature worktree removed

## Objective

Give one PC-SDK engine exclusive ownership of one canonical app data directory
for its entire lifetime. Admission must succeed before the product database,
migrations, boot recovery, runtime composition, or HTTP/WS listener can start.
A second engine targeting the same directory fails closed with an explicit
typed result, while engines using distinct directories remain independent.

## Requirements and boundaries

- Requirement ID: the data-directory admission half of `OPS-005`.
- Boundary documents: `docs/architecture/boundaries.md`,
  `docs/worktree-lifecycle.md`, and `docs/pickup-protocol.md`.
- Launcher/operations owns process and data-path admission. Product database
  state and component recovery remain owned by persistence/recovery.
- The lock is a non-replaceable kernel IPC witness (Windows named pipe or Linux
  abstract socket) paired with OS-enforced SQLite file ownership in a dedicated
  admission file, not a PID, heartbeat, age, port, or timeout heuristic.
  Process death releases both live locks through the operating system; stale
  metadata never authorizes takeover.

This slice does not implement the cross-process repository lease that completes
`OPS-005`. It also does not change child-process environment policy
(`SEC-003`), listener binding (`OPS-006`), accessibility, packaging, shortcut
installation, or daily-driver promotion.

## Canonical decisions

The admission database is separate from the product database. Admission first
binds a SHA-256-addressed kernel IPC name that cannot be replaced through data-
directory unlink/rename, then a dedicated `better-sqlite3` connection opens the
in-directory file with `timeout: 0` and holds `BEGIN IMMEDIATE` for the engine
lifetime. IPC `EADDRINUSE` or SQLite busy/locked is positive contention
evidence, but not owner identity. Open, permission, path, integrity, or
unsupported-platform failures are typed unavailable and cannot fall through
into application startup.

The paired live kernel/SQLite locks are authoritative. No persisted PID or
timestamp can prove ownership, so none is used to reclaim the directory. After
a hard crash, a new process may proceed only when both locks are positively
granted. The persistent admission file is retained; corruption is evidence to
stop, not permission to delete and retry. Production restart keeps the kernel
witness until actual process exit; its replacement may retry contention but can
proceed only on a later positive acquisition. A retry bound can only fail the
restart and never imply ownership.

## Acceptance criteria

1. Source and process guards prove admission occurs before `runMigrations`,
   boot recovery, runtime/provider initialization, and HTTP/WS listen. A failed
   contender performs none of those actions.
2. Two independent processes targeting the same canonical directory cannot
   both receive an acquired receipt. An ordinary contender immediately receives
   `data-directory-occupied`; a restart waiter either positively acquires later
   or fails. No wait expiry is treated as success.
3. Different canonical directories can be held concurrently. Relative,
   normalized, and filesystem aliases of one directory collide on the same
   kernel witness and admission file.
4. Graceful release permits a successor, and forced holder termination permits
   a successor only after the operating system releases both live locks. PID
   reuse, missing metadata, pathname replacement, and elapsed time play no role.
5. Missing directories are created and canonicalized. Corrupt admission files,
   invalid paths, permission failures, and non-contention SQLite failures return
   `data-directory-unavailable` and do not start the engine.
6. Shutdown synchronously closes HTTP/WS and registry admission before runtime
   disposal snapshots, attempts every tracked runtime, and closes the product
   DB. Restart spawns a bounded waiter while the old kernel witness is still
   held; only actual process exit and a later positive acquisition admit it.
   Failed cleanup cannot authorize overlap or a replacement spawn.
7. The hidden launcher distinguishes occupied from unavailable startup exits
   without waiting the full health timeout and points to the exact data path and
   error log.
8. Focused cross-process tests, source/allowed-path audits, independent hostile
   review, full `pnpm ci:check`, sealed commit, guarded landing, ancestry/tree
   proof, post-merge gate, push, and teardown pass.

## Risk and recovery

- Primary risks: acquiring after a product mutation, allowing timeout/PID
  heuristics to become takeover authority, replaceable path-only locking,
  admitting work after a shutdown snapshot, allowing a replacement to acquire
  before old-process exit, or leaving child fixtures alive.
- Recovery: every ambiguous admission or release fails closed; process death
  lets the OS release live handles; failed gates preserve this worktree while
  `main` remains read-only.
