Status: complete

## Objective

Implement accepted `CHAT-007` and `CHAT-008` as one bounded N2 slice: every
nonterminal orchestrator turn has honest, replay-equivalent operational
feedback, and every visible tool call follows one guarded canonical lifecycle
with an app-minted stable identity, safe summary, explicit approval provenance,

## Canonical decisions

Normal tool transitions are:

```text
requested -> running -> succeeded | failed
requested -> approval-needed -> running -> succeeded | failed
requested -> approval-needed -> denied
requested -> denied
```

A positive result may synthesize the missing `running` transition immediately
before its terminal because execution is then proven. A turn/restart boundary
may exceptionally close `requested` or `running` as `failed` with a closed
`turn-ended` or `runtime-lost` reason; an unresolved `approval-needed` becomes
session-attributed `denied`. Terminal calls never transition again.

The durable tool event has no input, output, provider error, native ID, or
arbitrary prose. `safeSummary` is a deterministic function of the bounded tool
name. Approval state explicitly represents unknown, not-required, pending,
allowed, and denied with source and app request ID where applicable.

Activity phases are limited to facts PC-SDK can positively observe: turn
starting, requesting the runtime, responding, retrying, and compacting. Tool
events themselves supply requested/running/waiting-for-approval/reviewing-result
feedback. “Still waiting” is a local display derivation after silence, not a
periodic durable claim.

## Acceptance criteria

1. No provider-native tool ID, raw tool input/output, tool-input delta, private
   reasoning, or arbitrary provider status text crosses the canonical event
   contract or browser lifecycle source.
2. Every call starts at `requested`, uses one stable `callId`, keeps immutable
   name/turn/summary identity, follows an allowed transition, and becomes
   `succeeded`, `failed`, or `denied` before its turn terminal.
3. Direct execution, app approval, user denial, timeout/session denial, native
   auto-denial, result-without-progress, exception, interrupt, and restart paths
   preserve explicit approval/terminal evidence and never infer success.
4. Tool transition validation is enforced at persistence and browser projection
   boundaries; duplicate/regressive/conflicting/post-terminal observations fail
   closed without replacing accepted state.
5. Claim/start/runtime/status/tool observations produce only the closed honest
   activity taxonomy. Active UI shows current safe status, elapsed time, and
   queued count; silence becomes a visibly derived “still waiting” state.
6. Approval-needed is durable and replayable. The process-local answer waiter
   re-emits its bounded redacted ask on reconnect; process restart closes the
   call/turn rather than presenting a stale actionable approval.
7. Live delivery, shuffled delivery, reconnect replay, past-session replay, and
   exact outbox redelivery converge to the same activity/tool projection and
   rendering.
8. Previously persisted legacy raw tool events and provider-authored system
   notices remain retained for evidence but are hidden from product replay
   after migration; canonical high-water order remains continuous. Historical
   null-turn terminals remain replayable because their ownership cannot be
   safely inferred, while the DB rejects every such new write.
9. `tool_called` verification counts execution evidence, never a mere request or
   denied call, and agent transcripts use the same safe lifecycle.
10. Focused contract/DB/server/web tests, adversarial audit, visual QA, production
    web build, and full `pnpm ci:check` pass before guarded landing.

The browser/HTTP agent-transcript paths above were added after hostile review
proved they are part of acceptance criteria 7 and 9: every live, replay, and
specialist transcript consumer must cross the same strict canonical guard.

## Risk and recovery

- Risks: callback/stream observation races, a tool stranded behind a terminal,
  unsafe technical data persistence, stale approval after reconnect/restart, or
  legacy payloads breaking strict replay.
- Recovery: the adapter and turn runner normalize race order; DB guards reject
  illegal transitions; settlement closes open calls transactionally before the
  turn terminal; unsafe legacy rows become hidden; any failed invariant preserves
  this branch/worktree and leaves landed `main` untouched.
