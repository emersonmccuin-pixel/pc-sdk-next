# CX-004: Fake-only Windows containment qualification

Status: blocked

## Objective

Implement and lab-qualify the ADR-0002 Windows lifecycle-containment foundation
using only deterministic fake processes, fake principals, disposable state, and
synthetic repositories. The successful outcome is a fake-lab qualification
receipt. It is never production admission and it never authorizes Codex or another
provider process.

Native, TypeScript, database, migration, product-test, and production-composition
implementation is not yet allowed. ADR-0002 makes the final immutable disposable-
runner identity and image digest a pre-product-code input. The qualification bootstrap
that creates that final image is a distinct earlier gate below; it is also blocked
because no accessible generalized source VHDX or authorized VM lifecycle is available.

## Runner provenance and admission protocol

The trusted lab controller is the repository-owned host-side script
`packages/windows-containment/lab/controller.ps1`; the provisioning-sealed guest
witness is `packages/windows-containment/lab/guest-agent.ps1`. The controller is run
by the separately authorized Hyper-V lab principal. It is qualification
infrastructure, not a third production PE or a continuing lifecycle process. Its
exact source, module closure, configuration, host identity, ECDSA P-256 public key,
and public-key SHA-256 are sealed before Q2 product implementation or any runtime use. The guest agent's image,
SID/token/privilege vector, process-object access, pipe policy, and native module
closure are sealed in the same manifests; it has only the query, synchronization,
peer-identity inspection, and preselected termination rights used below. The private key remains
outside the guest and PC-SDK repository. The controller holds no provider, project,
Git-remote, or application credential.

For every run the controller must, in this order:

1. open the offline parent VHDX and every manifest through retained identity handles
   whose sealed share mode permits the qualified Hyper-V read open but denies write
   sharing and delete/rename; the parent ACL, owner, read-only attribute, volume/file
   id, USN, size, and pre-hash must deny controller/guest write, delete, DACL, owner,
   or reparse authority;
2. prove the parent is unmounted and not attached to another VM, byte-hash every
   input through those handles, then retain them and re-prove identity/USN/size/hash
   after VM teardown; the sealed offline pnpm/Node/header/tool store is baked into a
   read-only parent path and independently covered by both store and parent digests;
3. create one unique differencing child and one Generation 2 VM with Secure Boot,
   fixed sealed CPU/memory/storage configuration, no network adapter, no enhanced
   session, clipboard, drive, guest-service, or host-filesystem sharing, and a unique
   VM GUID/run id;
4. create one controller-owned witness COM-port named-pipe channel plus one closed
   Hyper-V-socket service bound to that exact VM GUID and the provisioning-sealed
   service GUID, attach the exact digest-bound read-only source ISO, then boot only
   that VM;
5. execute the closed challenge/admission transcript below; and
6. retain the VM/process/storage/source identities through test completion, independently
   observe the guest result and artifact/evidence digests, power off the exact VM,
   delete the differencing child, and prove the VM, pipe, disk, and process state
   absent before reporting teardown success.

The source ISO is generated from one clean feature commit/tree and contains only a
canonical file manifest, bounded source/content files, fixed qualification plan, and
their hashes—never `.git` credentials, provider/login homes, user data, or writable
secrets. Its UDF/ISO identity, byte length, SHA-256, commit, tree, path grammar, file
count, per-file/total-size bounds, and no-symlink/reparse/device/alternate-stream facts
are in the run receipt. The provisioning-sealed guest lab agent copies it once into a
fresh child-disk staging root, verifies every file before and after copy, runs only the
fixed offline build/test plan, proves every build helper exited, and then acts solely
as the external process-handle witness plus the one-shot kill actuator defined below.
It holds no job, product witness, DB, project, or provider handle. It is qualification
infrastructure, not an admitted runtime helper.

Evidence returns only over the witness COM channel as fixed-order agent-session AEAD frames
within the sealed frame/aggregate bounds. Each frame binds run id, monotonically exact
sequence, kind, offset, total length, chunk SHA-256, and rolling evidence-manifest
digest. The controller accepts no path or command from the guest, acknowledges each
frame exactly once, requires the final manifest/byte digest, and retains the bytes in
the run evidence directory. No host share or post-test mounting/parsing of the
untrusted child disk substitutes for this channel.

Both repository-native PEs embed the admission-root digest and controller public key.
On resume, `entry-scrub` first arms and positively queries its accepted independent
native hard-deadline watchdog; creation/query failure immediately exits, and the
watchdog has no external input, cancel, reset, or extension path. After that positive
first-fallible-action receipt and before `CreateJobObject`, product named-pipe witness
creation, SQLite open, child process creation, or any other product-boundary mutation,
scrub performs only bounded hard-gate/identity reads and this closed one-run transcript:

1. After build helpers are zero, the lab agent requests `LaunchIntent`; the controller
   durably issues a nonsecret unique 128-bit launch id bound to the exact
   run/VM/role/generation/attempt but no capability. The agent creates exact
   `entry-scrub` suspended with `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` containing only the
   separately enumerated sealed standard-I/O handles—no capability or ambient inherited
   handle. It independently queries PID/creation/image, handle rights, and creation
   inputs, sends authenticated `LaunchCreated`, and does not resume. Only after the
   controller cross-binds the retained observation handle and exact creation receipt
   does it return `ResumeAuthorized`; the agent requires `ResumeThread == 1`, closes
   the thread handle, and sends `LaunchReady`.
2. After watchdog arm/query and the exact unjobbed scrub hard-gate query, scrub's next
   bounded actions are the sole pre-admission mutation exception: it
   generates a 256-bit nonce, creates one local one-instance byte-mode capability-pipe
   server named `\\.\pipe\PCSDK-CX004-CAP-{run}-{launch}-{nonce-hex}` with
   `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`, no inherited handle,
   and the manifest-sealed descriptor, then opens one outbound `AF_HYPERV` connection
   to the exact sealed controller service/VM GUID. It exposes no listener except that
   one local pipe and has no IP network adapter, alternate service, inherited socket,
   or reconnect fallback. `ChannelReady` binds the exact pipe name/nonce, launch id,
   independently queried process identity, and watchdog-ready TID/descriptor/deadline/
   observation digest but is not authentication.
3. After matching `ChannelReady` to the still-issued launch and independent agent
   process/thread-handle watchdog observation, the controller sends one ECDSA-signed
   `DeliveryDirective` binding the exact run/VM/launch/role/generation/attempt,
   pipe/nonce, target PID/creation/image, sealed agent PID/creation/image, five-second
   expiry, and a new 256-bit delivery challenge. Scrub verifies the signature/expiry
   before accepting a pipe client. The controller separately generates a unique
   256-bit `BCryptGenRandom` capability and sends it only inside the admitted agent
   session's AEAD channel. The agent connects to the exact pipe, requires
   `GetNamedPipeServerProcessId` plus retained-handle creation/image to equal the target,
   and scrub requires `GetNamedPipeClientProcessId` plus a least-rights process query to
   equal the signed agent PID/creation/image. Scrub positively closes that temporary
   agent-query handle and proves it absent from its handle inventory before continuing;
   close/query uncertainty is unsupported. After both peer-PID
   receipts, the agent writes exactly one capability record and EOF; scrub reads it
   directly into a successfully `VirtualLock`ed fixed allocation, requires EOF, and
   closes the pipe. The agent closes its pipe handle, computes the fixed delivery
   digest, zeroizes the capability, and sends agent-session-key HMAC
   `CapabilityDelivered`; scrub sends `CapabilityLoaded`, binding the peer-query close
   receipt and HMAC-SHA-256 under the
   capability over ASCII domain `PCSDK-CX004-DELIVERY\0` plus the exact directive and
   channel tuple within both a five-second controller-monotonic expiry and an
   independent five-second guest-monotonic directive-to-load bound. The controller
   requires both matching receipts plus pre/post system-
   handle inventories showing no extra pipe handle before it records delivery `loaded`.
   No product spawner receives capability bytes or a capability-pipe handle.
4. Only after that socket-to-process binding does the controller generate a unique
   256-bit challenge, record it `issued` in the durable replay ledger, and send
   `Challenge` on the same socket. Challenges expire after 30 controller-monotonic
   seconds and are never reissued.
5. Scrub generates its own 256-bit admission nonce with `BCryptGenRandom`, independently queries
   its PID/creation/image and the complete guest/root-manifest facts, and sends one
   `AdmissionRequest` binding run, VM, admission challenge/nonce, delivery-directive
   and `CapabilityLoaded` digests, launch id/identity, source ISO, artifact hashes,
   admission-root digest, native probe, and a launch proof. The proof
   is HMAC-SHA-256 under the delivered capability over ASCII domain
   `PCSDK-CX004-LAUNCH\0` followed by the exact canonical request bytes through the
   final non-proof field; the fixed proof field is omitted.
6. The controller matches every request field to its retained host/VM/source/process,
   spawner, and witness-handle evidence and verifies the launch proof in constant time.
   It generates a 256-bit per-channel session key, atomically marks both the challenge
   `receipted` and launch capability `consumed`, and returns one signed
   `AdmissionReceipt` containing the complete match, launch id/proof digest, exact
   expiry policy, session key, and initial sequence. A capability can authenticate
   exactly one accepted connection; a second/wrong connection, request, or consumption
   is typed unsupported and can never displace or receive credit for the target.
7. Scrub verifies the receipt within five guest-monotonic seconds of receiving the
   challenge, requires successful `VirtualLock` of the fixed session-key allocation,
   zeroizes the consumed capability, and atomically consumes the receipt before any
   boundary mutation. Missing,
   duplicate, reordered,
   stale, malformed, unknown-field, wrong-process, wrong-channel, mismatch, crypto,
   allocation, or timing uncertainty returns typed unsupported, zeroizes state, and
   exits.
8. Every later phase/evidence `Result` binds the delivery challenge/digest, admission
   challenge/nonce, exact process identity,
   monotonic sequence, phase/outcome, evidence length/count/digest, and terminal
   process/job/witness state under HMAC-SHA-256 with the session key. The controller
   verifies and durably consumes it, returns a matching HMAC `Ack`, and rejects any
   duplicate/gap/reorder/late/cross-run value. Scrub requires the exact ack, zeroizes
   the key, and closes the channel. Controller replay state survives until positive
   VM/evidence teardown and run close; run ids, challenges, and nonces are never reused.

The target's temporary agent-query handle is a distinct owned site in the generated/

ECDSA is P-256 over SHA-256; every static or ephemeral ECDSA/ECDH public key uses
65-byte uncompressed SEC1 encoding; signatures use exact 64-byte IEEE-P1363 big-endian `r || s`, require
`1 <= r,s < n` and low-S `s <= n/2`, and reject every alternate DER or malleable form.
The ECDSA digest covers ASCII domain `PCSDK-CX004-ADMISSION\0` followed by the exact
canonical `AdmissionReceipt` bytes from magic through its final non-signature field;
the fixed 64-byte signature field is omitted, never zero-filled or self-covered.
`DeliveryDirective` uses the identical construction with distinct ASCII domain
`PCSDK-CX004-DELIVERY-DIRECTIVE\0` and its own exact non-signature bytes.
`AgentHello` and `AgentAttestation` likewise use their distinct manifest-fixed ASCII
domains and exact non-signature bytes.
HMAC covers the manifest's exact message-specific ASCII domain, role/generation, and every canonical
frame byte through the final non-MAC field, omitting the fixed MAC field. All
controller, guest, signature-key, digest, and HMAC comparisons are constant-time.
Controller wall time is informational only; expiry uses its monotonic ledger and the
guest's local five-second monotonic response bound. The controller independently
verifies the challenge-bound result; neither a copied manifest nor self-reported
version is provenance.

Before any target `LaunchIntent`, the lab agent establishes a distinct nonrecursive
trust-root session over the controller-owned witness COM channel. Q1 creates one
non-exportable machine CNG ECDSA P-256 agent signing key whose key name/provider,
public key/digest, export-policy failure, protected key ACL, dedicated agent SID/startup
entry, executable/script/module hashes, and exact parent digest are sealed in the
provisioning/OS-security/admission-root manifests. This qualification-only key grants
no provider, host, project, network, or external-write authority. The controller's
separate private key remains host-only; its public key is embedded in the agent.

The wire manifest defines this four-message bootstrap independently of target
admission: controller-signed `AgentHello` binds run/VM/parent/configuration digests, a
fresh challenge/nonce, and an ephemeral ECDH P-256 public key; agent-signed
`AgentAttestation` binds that transcript, its fresh nonce/ephemeral ECDH key, exact
process/image/SID/token/key/boot facts, and the dedicated COM identity; encrypted
`AgentAccept` binds the verified transcript/session id/initial sequence; encrypted
`AgentReady` proves key possession and exact state. Both sides derive distinct
host-to-guest and guest-to-host `agent-aead-key`/32-bit nonce-salt pairs plus a separate
`agent-mac-key`, using manifest-fixed HKDF-SHA-256 labels over the ephemeral ECDH secret
and both nonces, then destroy the ephemeral private keys. In each direction, agent
frames use that direction's AES-256-GCM key/salt plus its independent strictly monotonic
big-endian 64-bit sequence as the 96-bit nonce, the exact canonical header as AAD, and
a 16-byte tag; key/salt/sequence state is never shared across directions and nonce/
sequence/key reuse is impossible. The controller durably
consumes challenge and session state before accepting `AgentReady`. A missing, second,
replayed, wrong-image/key/VM, decrypt, sequence, or teardown fact powers off the child
and admits no agent session.

Only that admitted agent session may carry encrypted capability bytes and witness
facts. `CapabilityDelivered` is HMAC-SHA-256 with `agent-mac-key`, is acked before the
agent erases its delivery digest, and never uses the target capability as its MAC key;
`CapabilityLoaded` is instead HMAC-SHA-256 with the delivered target capability. The
wire manifest gives every message an exact key selector and pre/post zeroization state.
Agent keys never enter a target and target keys never enter the agent. A fact crossing
the roles is accepted only when controller-retained run/VM/process/source identities
match independently on the trust-root and target channels. The immutable parent,
Secure Boot/OS TCB, sealed startup identity, protected non-exportable key, and dedicated
COM endpoint are the explicit agent trust root; target admission is never recursively
used to authenticate that agent.

After the final evidence/handle-close vector, the agent sends AEAD `AgentClose`, the
controller durably consumes it and returns AEAD `AgentCloseAck`, and both sides
zeroize/retire all agent-session material before VM power-off. Loss or close uncertainty
is inconclusive; positive exact-VM power-off/destruction still occurs but is not
mislabeled as a clean channel close.

Every executable role and generation—`entry-scrub`, cold bootstrap, owner,

every name, `=`, value, per-entry NUL, and final extra NUL. Duplicate-equivalent keys

`KiB` and `MiB` mean 1,024 and 1,048,576 bytes. Frame caps cover the complete on-wire

also to the sum of all collection members in one request, receipt, or manifest.

overlapped operations, and callback delivery buffers; duplicated bytes count once per
physical copy. Directional caps apply to that aggregate direction, and the 3 MiB cap
applies across all three directions and layers. The 32 MiB stress value is logical
streamed traffic per direction and may never be resident as one buffer. File/artifact
caps count exact file bytes. Deadlines use one monotonic clock from the named
transition and include cleanup time unless a distinct settlement bound is stated.

entry point reads only fixed-size length/header scalars, rejects values above the raw
cap, and uses checked `size_t` add/multiply for terminators, quoting, escaping, and
worst-case encoding expansion. N-API string length is queried before buffer allocation;
frame length is validated from the fixed header before payload allocation; UTF-8/
UTF-16 is decoded by a fixed-cap streaming validator; and Windows command-line quoting
performs a counting pass whose worst case includes doubled backslashes, escaped quotes,
separators, quotes, and final NUL before one exact allocation. Environment sorting uses
bounded indices into the already capped block. Overflow, truncated raw input, or an
expansion above the final cap fails before reading/copying the claimed body. Boundary
tests instrument the allocator and prove zero input-sized allocation before this
preflight for zero, cap, cap-plus-one, `SIZE_MAX`, fragmented, and malicious headers.

case-insensitive comparator. The manifest records the canonical sorted sequence;
duplicate-equivalent keys, pseudo variables outside the closed allowlist, and

## SQLite restart durability contract

Two SQLite roles remain distinct. `.pc-sdk-next-admission.sqlite` is only the
zero-wait process-exclusion lease paired with SF-001. It uses the exact verified
binding, `busy_timeout=0`, `locking_mode=NORMAL`, `journal_mode=DELETE`,
`synchronous=FULL`, and one held `BEGIN IMMEDIATE`; it stores no restart truth and
never supplies a success inference. The old owner positively closes it before the new
owner can acquire it. Bootstrap never opens either database.

The `owner_restart` row and matching canonical outbox/control event live in product
`pc.sqlite` and commit in one transaction owned only by the owner-lifecycle component.
Every open uses exact `better-sqlite3@11.10.0` / SQLite `3.49.2` through the sealed
singleton factory and verifies this fixed policy before a transition:

| Fact | Required value |
| --- | --- |
| `journal_mode` | `WAL` |
| `synchronous` | `FULL` (`2`) |
| `wal_autocheckpoint` | `0` |
| `busy_timeout` | `0` during restart transition |
| `locking_mode` | `NORMAL` |
| page size | 4,096 bytes |
| extension loading | unavailable for the full connection lifetime |
| checkpoint | explicit `wal_checkpoint(TRUNCATE)` after each successful transition commit |

`prepared`, `committed`, `aborted`, `completed`, interrupted reconciliation, and
attention first require the component-owned restart-transition lease, stopped external
admission, all other product-DB consumers quiesced, and exactly one verified product-
DB connection. They then execute: `BEGIN IMMEDIATE`;
nonce/old-generation/new-generation/current-
state CAS; exactly one idempotency-keyed row mutation; exactly one matching outbox
insert; invariant and affected-row checks; then `COMMIT`. A successful commit return
must include SQLite's Windows VFS `xSync`/`FlushFileBuffers`-equivalent behavior under
`synchronous=FULL`; JavaScript read-back is not a flush and no owner-authored flush is
accepted as a substitute.

After commit, admission remains stopped while the owner requires
`wal_checkpoint(TRUNCATE)` to return exactly `busy=0`, `log=0`, and
`checkpointed=0`, closes every product-DB connection without error, verifies the
connection closed, reopens through the same sealed factory, re-verifies every pragma,
and reads the exact row/event pair and digest. It then closes again. Old owner may
publish the corresponding handoff fact only after that sequence. New owner performs
the same sequence for `completed` after bootstrap has positively exited and before
opening product services or the ordinary product-DB lifetime connection.

`BUSY`, `LOCKED`, `IOERR`, short/partial result, close error, unexpected checkpoint
counts, pragma drift, missing/duplicate/mismatched row/event, or any uncertain return
publishes no transition success. The operation records or recovers as uncertain,
terminates/quarantines according to the handoff phase, and boot reconciliation reads
durable truth without replaying restart. It never rolls a state backward or creates a
replacement outbox event from memory.

The owner-lifecycle transition core has a closed qualification-barrier port at named
application boundaries: transaction entered; row statement returned; outbox statement
returned; immediately before `COMMIT`; successful `COMMIT` returned; immediately
before checkpoint; checkpoint returned; immediately before close; close returned;
