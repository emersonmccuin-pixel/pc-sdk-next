## Current Windows Sandbox runner Q0S

Q0S is the only current pre-product runner gate. Windows Sandbox is a built-in Windows
Pro entitlement that dynamically uses the host Windows image, launches a separate
kernel, and discards session state at close. The accepted simplification deliberately
replaces byte-for-byte custom-image provenance with exact observed host/guest identity,
sealed Sandbox configuration/input provenance, positive session lifecycle, and a safe
same-host smoke. It makes no production-image or physical-power-loss claim.

### Staging and hardened Sandbox configuration

Safe probe compilation, static analysis, and input-bundle assembly run provider-free
on the observed host with the sealed local toolchain. Each run uses a new private root
under `%LOCALAPPDATA%\PC-SDK-Next\cx-004-runs\<runId>` containing:

- one closed input directory with the exact fixed bootstrap, deterministic fake
  fixtures, probe or later product artifacts, portable runtime/test files, stable-file
  manifest, and one dynamic run manifest carrying the run id/challenge; and
- one new empty results directory writable by the Sandbox and containing only synthetic
  test evidence.

The harness refuses mapping the user-profile root or any source outside that newly
created dedicated run descendant, plus any repository path, PC-SDK data directory,
provider/login home, real project, pre-existing result, reparse point, unexpected hardlink/
alternate stream, or broad writable input. The repository is never mapped. Input is
mapped read-only at `C:\CX004\input`; the new empty evidence directory alone is mapped
read/write at `C:\CX004\output`. Windows Sandbox has no write-only mapping: guest read
access to that empty nonsecret directory is an explicit residual. Every returned byte
is untrusted and accepted only through a closed file/count/size/schema/hash manifest.
The Windows PowerShell 5.1 mapped-input probes retain the raw outer/immediate-inner
exception types, signed HRESULTs, and deeper-inner presence. Read-only proof admits only
the exact observed two-node denial chain `MethodInvocationException (0x80131501) ->
UnauthorizedAccessException (0x80070005) -> no deeper exception`, together with no
created artifact and unchanged sealed-input hashes. Any other error shape is
inconclusive; successful write/open or mutation is a positive failure.
Both canonical host paths, volume/file identities, ACLs, contents, and hashes are
sealed before start and re-proved after exact-ID stop.

The source-sealed `.wsb` template/schema digest permits only the two declared canonical
host mapping-path substitutions. Each separately hashed rendered XML instance
contains exactly the two mapped folders, one fixed absolute `LogonCommand` bootstrap,
fixed 4,096 MiB memory, and these requested settings:

- networking disabled;
- vGPU disabled;
- clipboard redirection disabled;
- audio input disabled;
- video input disabled;
- printer redirection disabled;
- Protected Client enabled; and
- 4,096 MiB configured memory.

Startup rejection, an extra XML element/folder/device mapping, an undeclared routable
non-loopback adapter/default route, successful connection to the fixed host/external
DNS/raw-IP canaries, host-path write through the input share, or stable-template delta
fails Q0S. The guest runs independent negative
network/input-write probes and the host validates their challenge-bound results. vGPU,
Protected Client, clipboard, audio/video, and printer settings are recorded as exact
requested defense-in-depth configuration because Microsoft exposes no independent
guest/CLI attestation; they are never mislabeled as effectively queried. The bootstrap
first copies the closed input into guest-local
scratch and re-verifies every hash before execution. The harness exposes no post-start
command or path execution interface. It makes one exact-ID `connect` call solely to
establish the documented remote container-user logon that triggers the fixed
`LogonCommand`; the temporary protected RDP window, mouse/keyboard state, and any user
interaction are untrusted and never evidence. The harness never calls `exec` or `share`.
The reviewed `connect` launcher can leave its stdout/stderr pipe writers inherited by
the long-lived remote-session child after the launcher exits. The bounded host runner
therefore cancels and closes only its own readers after a finite drain interval, proves
both collectors settled, and discards any incomplete connect text. Connect output and
window state are always opaque non-evidence; only the challenge-bound guest terminal
receipt proves that logon and bootstrap execution occurred.

### Session, matrix, and teardown receipt

For every Q0S readiness run the host harness:

1. generates a fresh run id and 256-bit challenge, seals the stable template/fixed input
   plus dynamic rendered-config/run-manifest/result facts, and proves no running Sandbox
   session while recording any stopped/history rows;
2. reads the canonical `.wsb` XML as one exact argument and starts exactly one session
   with `wsb start --config <exact-xml> --raw`, retains its returned session id,
   requires `wsb list --raw` to show that returned id as the sole running identity,
   then invokes only `wsb connect --id <retained-id> --raw` to establish the active
   user session required for the fixed `LogonCommand`; after a finite output-drain
   interval the harness closes and settles its own connect readers, discards incomplete
   text without interpreting empty output as EOF, and only challenge-bound guest terminal
   evidence proves logon/bootstrap execution;
3. allows only the `.wsb` `LogonCommand` to start the fixed absolute bootstrap; no
   `wsb exec`, arbitrary command, shell/PATH lookup, or third mapping is permitted;
4. has the guest re-prove its OS/token identity, requested-config digest, observable
   network/input isolation probes, empty persistence canary, challenge, manifests, and
   every stable input hash before loading code;
5. runs the fixed Q0S lifecycle/configuration probe and writes bounded challenge-bound
   synthetic results; the host requires a terminal guest receipt and independently
   parsed result equality;
6. creates one guest-local persistence canary, stops only the retained id with
   `wsb stop --id <retained-id> --raw`, requires `wsb list --raw` to return an empty
   running-session list, closes every harness-owned handle, and proves
   mapping release through exclusive file-open and output-directory rename-and-back;
7. starts a second fresh session from the same sealed template and fixed probe bytes,
   with a new dynamic run manifest, run root, rendered XML, output, run id, and challenge;
   requires the second returned canonical Sandbox session id to differ from the first,
   proves the non-mapped canary absent; then positively stops and proves that session no
   longer running; and
8. re-proves both read-only inputs unchanged and accepts only each run's declared result
   files.

Timeout, window disappearance, generic process exit, or elapsed time never implies
teardown. A pass records `teardownLevel=sandbox-session-stopped`: terminal evidence,
exact-id stop success, no running returned-id entry, harness-owned handle and mapping-
release proof, unchanged input, and validated output, together with Microsoft's
documented stop/discard semantics. It does not
claim hidden VM/disk identity or independent disk destruction. An unknown session,
uncertain exact-id stop/mapping close, result outside the allowlist, late write, or stale
canary makes the run inconclusive and preserves evidence unless an independently proven
positive boundary violation already requires `failed`. A positive violation is never
downgraded by later evidence uncertainty, while its teardown claim remains `unproven`.

Raw machine/user names and SIDs, absolute profile paths, boot timestamp, challenge,
session ids, and complete CLI output remain only in one canonical quarantined local-
evidence bundle. The tracked receipt binds only the bundle's aggregate SHA-256, whose
preimage includes the fresh challenge, plus redacted aliases and nonpersonal semantic
fields. It never commits standalone unsalted hashes of enumerable usernames, SIDs, or
profile paths. Guest well-known account semantics may be named; machine-derived identity
material remains only inside the aggregate bundle.

The later final fake-lab lane may terminate a fake owner process at a challenge-bound
synthetic SQLite boundary. The database remains on guest-local storage; after the kill,
an independent guest witness starts the deterministic recovery reader, closes SQLite,
and only then emits bounded evidence to the mapped output. No active WAL/SHM/database
resides on the redirected mapping. This proves abrupt process-loss recovery only. It is
not a physical host power-cut or storage-cache receipt; independent physical-power-loss
testing is an accepted unclaimed daily-driver residual, not a production blocker.

### Safe same-host smoke

Q0S additionally runs one bounded provider-free host smoke against only its cooperative
probe and a new synthetic temp root. It creates one fake child suspended into a
kill-on-close leaf Job Object with `bInheritHandles=FALSE`, positively queries exact PID
membership, retains only its explicit harness-owned job/process/thread handle ledger,
resumes once, closes the sole job handle, and proves the child signaled, marker stopped,
handle cleanup, and temp-root release within 30 seconds. It never starts a provider,
opens an app DB/login home/real project, changes policy, kills the PC-SDK server, injects
power loss, or uses unbounded/PID-tree cleanup. It is recorded as `host-smoke-only` and
does not qualify a grandchild escape, hard-killed owner, SQLite reset, production
topology, or CX-004 product behavior. The final product artifacts later repeat the
applicable bounded host smoke; all destructive cases stay inside Sandbox.

### Q0S limitation and gate sequence

Q0S qualifies only the runner/configuration/lifecycle probe on the exact observed host/
Sandbox tuple. The later final fake-lab receipt qualifies the implemented deterministic
fake-process matrix on exact sealed product artifacts. Neither result qualifies a
custom Windows image, protected production install, code-integrity or
postmortem policy, arbitrary pre-existing same-user malware, provider credentials,
external actions, CX-008 two-tier isolation, physical power loss, or a real provider.
No Sandbox receipt substitutes for the later fresh production OS/protected-install/
provider-policy receipts already required by ADR-0002.

The sequence is fixed: (1) land this amendment; (2) announce and perform the one UAC-
approved Sandbox feature enable, restarting only if Windows reports it required;
(3) host-only discover the modern CLI/package without starting a session; (4) implement/
review/land the harness and fixed probes as `S0`; (5) run Q0S from re-fetched `S0` and
land run evidence `R0` plus post-landing closeout `R1`; (6) implement the native/
TypeScript product; and (7) run the complete final fake matrix in fresh revalidated
Sandbox sessions before CX-004 can close.

Every applicable bound requires zero, exact-bound, bound-plus-one,
huge/wrap-shaped, allocation-failure, embedded-NUL, invalid-UTF-16, fragmented,
and coalesced cases.

All UTF-16 counts are unsigned checked counts after canonicalization and rejection of
embedded NUL, unpaired surrogate, lossy, or noncanonical input. The application cap
allows the same canonical path to appear as quoted `argv[0]`: command-line accounting
includes both quotes, all required escaping/separators, and the final NUL. Logical
argument/name/value counts exclude separators and terminators unless the table says
otherwise. Environment entry count includes every admitted drive-current-directory
pseudo variable; name/value caps exclude `=` and NUL, while the block cap includes
every name, `=`, value, per-entry NUL, and final extra NUL. Duplicate-equivalent keys
are rejected before counting.

`KiB` and `MiB` mean 1,024 and 1,048,576 bytes. Frame caps cover the complete on-wire
encoding—header, length/type fields, payload, authentication/integrity data, and any
trailer—not merely the payload. The collection cap applies to each list/map/set and
also to the sum of all collection members in one request, receipt, or manifest.
Stdio caps count every resident copy across JavaScript queues, native queues, pending
overlapped operations, and callback delivery buffers; duplicated bytes count once per
physical copy. Directional caps apply to that aggregate direction, and the 3 MiB cap
applies across all three directions and layers. The 32 MiB stress value is logical
streamed traffic per direction and may never be resident as one buffer. File/artifact
caps count exact file bytes. Deadlines use one monotonic clock from the named
transition and include cleanup time unless a distinct settlement bound is stated.

Before any input-derived allocation, copy, canonicalization, or OS mutation, each
entry point reads only fixed-size length/header scalars, rejects values above the raw
cap, and uses checked `size_t` add/multiply for terminators, quoting, escaping, and
worst-case encoding expansion. N-API string length is queried before buffer allocation;
frame length is validated from the fixed header before payload allocation; UTF-8/
UTF-16 is decoded by a fixed-cap streaming validator; and Windows command-line quoting
performs a counting pass whose worst case includes doubled backslashes, escaped quotes,
separators, quotes, and final NUL before one exact allocation. Environment sorting uses
bounded indices into the already capped block. Overflow, truncated raw input, or an
expansion above the final cap fails before reading/copying the claimed body. Boundary
tests instrument the allocator and prove zero input-sized allocation before this
preflight for zero, cap, cap-plus-one, `SIZE_MAX`, fragmented, and malicious headers.

Environment keys use one explicitly implemented Windows ordinal
case-insensitive comparator. The manifest records the canonical sorted sequence;
duplicate-equivalent keys, pseudo variables outside the closed allowlist, and
any lossy encoding are unavailable.
