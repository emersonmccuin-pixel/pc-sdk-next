# RS-003: Immutable specialist execution snapshots

Status: complete — sealed, awaiting guarded landing

## Objective

Complete the specialist half of the N3 runtime-selection invariant. Every new
agent run must freeze the execution-effective specialist revision and one
complete runtime/account/model/effort selection before provider or repository
work begins. Native create/resume identity advances only from an exact durable
attempt receipt, and continuation/revival always uses the frozen run evidence
rather than a mutable roster row.

## Canonical decisions

The run-owned `SpecialistExecutionSnapshot` contains only execution-effective
specialist material consumed by today's dispatch path: specialist id, opaque
revision, name, charter, ordered context documents, and effective maximum
turns. The issued Contract already freezes expected output and acceptance;
`RuntimeSelection` freezes model and effort. Fixed app tool wiring remains
code-owned. Secrets, credential values, provider payloads, and future MCP or
permission compilation never enter the snapshot.

A fresh dispatch resolves the current visible specialist once, captures its
snapshot, and asks the composition-owned resolver for a complete selection.
Resolution or preflight failure refuses before worktree provisioning or any
durable run/contract mutation. Production may still choose Claude as its only
registered default, but dispatch receives that policy and never imports or
branches on `CLAUDE_RUNTIME_ID`.

Every continuation row inherits the parent's exact snapshot and selection.
The live roster may be read only to compute optional drift evidence; it cannot
alter the instructions, model, effort, account, runtime, or maximum turns used
for continuation. A paused run revived after restart likewise reconstructs
from its own frozen row.

New rows use provider-neutral continuation states. Fresh rows begin unbound;
continuation rows may inherit a positively bound parent native identity but
remain resume-pending until an exact positive receipt. Immediately before an
adapter call, the repository rotates a non-empty attempt generation. Receipt
confirmation compares app run, selection, attempt, mode, requested identity,
and current durable state in one transaction. Matching redelivery is
idempotent; all other evidence writes nothing.

Legacy rows lack a provable effort and execution snapshot. Migration therefore
does not promote their existing runtime/account/model/native-looking values
into truth. They become `legacy-unavailable`, remain readable, and cannot be
continued or revived. Boot recovery closes any legacy paused ask through the
existing canonical terminal/publication path while retaining repo worktree
evidence for explicit recovery.

## Acceptance criteria

1. Every new specialist/reviewer dispatch captures and adapter-validates a
   strict snapshot/selection before repository mutation, then persists that
   exact tuple before native execution; DB guards reject incomplete or later-
   mutated stamps.
2. Fresh dispatch, provision failure, manual/automatic continuation, paused
   revival, and independent review all use one composition/registry selection
   path; dispatch contains no concrete provider selection/import.
3. Editing/deleting a specialist or changing project/account/default model,
   effort, charter, context, or turn limit after dispatch cannot change a
   continuation or restart revival. The parent snapshot/selection is exact.
4. Every native create/resume rotates a durable attempt before the call. Only
   an exact positive receipt can bind/confirm identity; stale, late, malformed,
   wrong-mode, mismatched-selection, or conflicting receipts write nothing and
   cannot announce a run as running.
5. Migration invents no legacy selection/snapshot truth. Legacy rows remain
   visible and non-resumable; legacy paused asks close visibly at boot and
   repository work is preserved.
6. Pending asks correlate by `agentRunId`; agent-run/pending-ask HTTP, MCP,
   websocket, and browser DTOs contain no native session or attempt identity.
7. Safe run projections expose the complete selection, specialist revision,
   native identity presence only, and honest clean/resume/legacy provenance.
   Exact-shape guards reject extras or malformed nested data.
8. Existing contract, worktree, ask, recovery, review, auto-continue, and
   terminal semantics remain green with focused adversarial tests.
9. Diff/source-boundary audits, independent hostile review, production web
   build when presentation changes, and full `pnpm ci:check` pass before a
   sealed commit and guarded landing.

## Risk and recovery

- Primary risks: treating placeholder native IDs as evidence, guessing legacy
  effort/account/runtime, resolving a mutable pod during continuation, missing
  the paused/reviewer resume paths, or accepting a receipt after kill/service
  replacement.
- Recovery: selection/preflight stops before mutation; immutable snapshot and
  selection guards reject drift; attempt CAS rejects stale evidence; legacy
  rows fail closed; repository failure preserves the branch/worktree; any
  failed gate leaves this feature worktree intact while `main` stays read-only.
