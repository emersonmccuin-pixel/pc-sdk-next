# DL-001: Positive preparation and readiness receipts

Status: complete — guarded-landed, verified, pushed, and cleaned up

## Objective

Close the characterized builder-lifecycle gap where an absent setup or
readiness command list is currently represented by a missing receipt. Every
repository builder run and continuation must persist explicit positive
preparation and readiness receipts before its provider runtime can mint or
send. A configured command phase records executed evidence; an intentionally
skipped phase records why it was not required. Missing, failed, malformed, or
stale evidence never means success and preserves the worktree.

## Canonical receipt contract

An executed phase records:

```ts
{
  phase: 'preparation' | 'readiness';
  outcome: 'executed';
  ok: boolean;
  steps: WorktreeCommandStep[]; // non-empty
  finishedAt: number;
}
```

A positive no-op records:

```ts
{
  phase: 'preparation' | 'readiness';
  outcome: 'not-required';
  reason: 'no-commands-configured' | 'existing-worktree-preparation';
  inheritedFromRunId?: ULID; // required only for existing-worktree preparation
  ok: true;
  steps: [];
  finishedAt: number;
}
```

`executed` is positive only when `ok` is true and every step has exit code
zero and is not timed out. `not-required` is positive only for its exact shape
and reason. Receipt phase, reason, parent identity, timestamps, and step fields
are validated rather than trusted from TypeScript types.

## Acceptance criteria

1. Fresh null, fully empty, cleanup-only, and base-branch-only profiles record
   preparation and readiness `not-required/no-commands-configured` before the
   runtime mint.
2. Setup-only and readiness-only profiles record one executed phase and one
   explicit no-op; a profile with both records two executed receipts.
3. A continuation always records preparation
   `not-required/existing-worktree-preparation` bound to its parent run, then
   re-runs configured readiness or records a readiness no-op on the new row.
4. Setup failure records only the failed preparation receipt. Readiness failure
   records positive preparation plus failed readiness. Neither path mints a
   runtime, and the worktree is preserved.
5. Cancellation or a race between phases cannot append evidence to a terminal
   run or mint a runtime. The missing later phase stays honestly absent.
6. Repository runtime mint and paused-run revival refuse missing, malformed,
   negative, phase-mismatched, or worktree-mismatched Git/phase evidence.
7. Valid legacy command-bearing receipts migrate exactly to `executed`; null,
   empty-step, malformed, runtime-incompatible, and discriminator-forged
   legacy values are not promoted. Historical agent-run outbox frames are
   invalidated while unrelated resource replay is retained.
8. Non-repository runs and detached reviewers retain their current null phase
   semantics and cannot be cited as satisfying the remaining `WT-002` scope.
9. Focused checks, actual-path audit, `git diff --check`, hostile review, full
   `pnpm ci:check`, sealed commit, guarded landing, ancestry/tree proof,
   post-merge gate, exact push, and worktree teardown pass.

## Risk and recovery

- Primary risks: treating empty steps as success without a reason, mutating a
  receipt after runtime start, fabricating historical no-ops, losing a
  cancellation race, or applying the builder receipt to a different checkout.
- Recovery: invalid/missing evidence prevents runtime mint, fails loudly, and
  preserves the isolated worktree. A failed gate leaves this feature worktree
  intact while `main` remains read-only.
