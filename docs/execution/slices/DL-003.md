Status: complete — implementation sealed and feature gate green; guarded

## Objective

Close the remaining bounded N4 recovery gap without creating a recovery center
or a second lifecycle database. Landed cleanup must remain retryable until the
worktree directory, Git registration, and merged feature branch are all
positively absent. Repository work stopped by preparation, verification,
cancellation, runtime failure, or server restart must remain durably reachable
in the existing Activity rail with honest evidence and explicit unavailable
states. A composed hard-kill test must prove two isolated worktrees converge
correctly after a real process death.

## Positive landed-teardown semantics

The landed contract receipt proves merge history, not cleanup. Cleanup is
complete only when all of these are positive for the exact durable binding:

1. current project repository identity matches the producer Git receipt;
2. the worktree row is the contract's one exact active/stranded row, or an
   already-destroyed exact row is being used only to finish a later lifecycle
   stamp after re-proving filesystem/Git absence;
3. the recorded worktree directory is absent;
4. a successful `git worktree list --porcelain` proves the recorded path is
   unregistered;
5. the exact landed feature branch is deleted by expected ref name, with an
   already-absent ref idempotently acceptable;
6. a successful exact ref query proves that branch is absent;
7. only then does an exact row CAS write `destroyed`; and
8. only after that proof may the producer and earlier preserved attempts reach
   lifecycle `completed`.

Filesystem fallback may remove only the already-authorized owned path. It must
still prove Git-registration absence. A locked/stale registration, branch
deletion failure, ref-query failure, row-CAS loss, or lifecycle-write failure
stays retryable and visible. `active` and `stranded` rows are both recovery
feeders. Stranded reconciliation may auto-resolve only a positively settled
DL-002 abandonment; landed cleanup remains owned by this exact proof chain.

## Browser recovery semantics

The existing project Activity rail gains one `Recovery required` region. The
strongest current evidence wins so a run, its contract, and its worktree do not
become three cards. Landing issue cards remain authoritative for conflict,
stale-base, mechanical landing failure, cleanup pending, and abandonment
pending/legacy. A stranded worktree card remains authoritative when it has no
stronger retained-run projection. Other retained/recent terminal outcomes use
the run card.

Closed labels include server restart, preparation failed, verification failed,
review rejected, run failed, cancelled, and stranded. Safe copy distinguishes
sealed evidence from an unsealed lost runtime and says work is preserved only
when an exact active/stranded worktree row supports that statement. `Inspect`
opens the existing transcript. `Abandon…` appears only through DL-002's current
eligibility and fresh server preview. The rail may instruct the user to ask the
orchestrator to continue/fix/re-dispatch, but adds no unaudited direct command.

Run-list and stranded-read failures are separate unavailable states. A later
successful seed clears the warning. HTTP reseed/live overlay ordering keeps a
terminal row as a tombstone against stale running frames while still making
the current terminal outcome visible in the recovery collection.

## Composed hard-kill gate

A provider-free child fixture uses a disposable data directory and real
temporary Git repository. It creates two isolated recorded worktrees and
durable contracts/runs, commits a sealed deliverable in one, leaves the other
unsealed and live, then waits. The parent positively observes that ready state,
hard-kills the process, and starts a fresh successor using the production boot
recovery order.

The successor must prove:

- the unsealed run fails once with `server-restart`, retains exact branch,
  directory, and content, and is returned by the recovery read;
- the sealed peer settles from its own deliverable stamp, re-verifies, lands
  once under the repository queue, proves ancestry, and completes positive
  worktree/registration/branch teardown;
- the two branches never cross-own rows or cleanup;
- a second boot writes no duplicate merge, terminal, or cleanup effect; and
- every fixture process, temp path, and repository lease is awaited and
  removed after positive shutdown/exit evidence.

The deterministic fake runtime is sufficient. No provider subscription call
is part of this gate.

## Acceptance criteria

1. A failed landed teardown remains selected on every later boot whether its
   exact row is `active` or `stranded`.
2. Directory absence without successful registration absence cannot settle;
   branch absence is also required before row destruction or `completed`.
3. Every cleanup crash window is idempotent and converges without a duplicate
   merge, cross-row mutation, false completed state, or lost retry.
4. Landed stranded reconciliation cannot bypass the cleanup proof chain.
5. Terminal exact owners of unresolved worktrees outlive the recent window;
   landing, receipt-backed abandonment, or ownership transfer removes them.
6. Recovery cards render restart/preparation/verification/review/failure/
   cancellation truth without exposing provider-native detail or claiming
   preservation without a durable row.
7. Run/worktree read failures remain visibly unavailable and retryable; they
   never collapse to zero recovery issues.
8. Collapsed Activity distinguishes running count from recovery count. Reload,
   reconnect, and stale-live redelivery do not duplicate or resurrect cards.
9. Inspect and existing DL-002 abandonment are the only browser actions. No
   continuation, Git repair, cleanup, MCP, chat tool, or generic mutation door
   is added.
10. The composed two-worktree OS hard-kill test passes the exact outcomes above
    and the existing kill/recovery matrices stay green.
11. Actual-path audit, `git diff --check`, independent hostile reviews, full
    `pnpm ci:check`, sealed commit, guarded landing, exact ancestry/tree proof,
    post-merge gate, exact push/re-fetch, and worktree cleanup pass.
